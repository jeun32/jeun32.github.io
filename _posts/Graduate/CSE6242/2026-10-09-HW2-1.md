지난 HW1에서는 흩어진 데이터를 수집하고, 정제하고, 데이터베이스에 저장해 분석하는 과정을 경험했습니다.

이번 **Data and Visual Analytics (CSE6242)의 두 번째 과제(HW2)**에서는 그 데이터를 **"어떻게 보여줘야 사람이 더 잘 이해할 수 있을까?"**라는 질문에 집중했습니다.

같은 데이터라도 표로 보여줄 때와 그래프로 보여줄 때 전달되는 정보가 다릅니다. 정확한 숫자를 비교하려면 표가 편하지만, 시간에 따른 변화는 선 그래프가, 복잡한 관계는 네트워크가 더 자연스럽습니다.

이번 전반부(Q1~Q3)에서는 **BoardGameGeek의 보드게임 데이터**를 가지고 세 가지 도구를 사용했습니다.

1. **Tableau**로 비교하기 쉬운 표와 막대그래프를 만들고,
2. **D3.js**로 보드게임 사이의 관계를 네트워크로 표현하며,
3. **Vega-Lite**로 시간에 따른 평가 수 변화와 순위를 시각화했습니다.

각 도구가 어떤 문제에 강하고, 구현 과정에서 무엇을 신경 써야 했는지 정리해 보겠습니다.

## <span style="color:#FEB99C;">1. 같은 보드게임 데이터, 서로 다른 질문</span>

차트를 만들기 전에 먼저 정리해야 할 것은 **"이 그림으로 무엇을 설명할 것인가?"**였습니다.

| 문제 | 도구 | 시각화 | 해결할 질문 |
|---|---|---|---|
| **Q1** | Tableau | 표, 그룹 막대, 누적 막대 | 어떤 종류의 게임이 많고, 플레이 시간과 인원에 따라 구성이 어떻게 달라질까? |
| **Q2** | D3.js | Force-directed network | 어떤 게임들이 서로 연결되어 있고, 연결이 많은 게임은 무엇일까? |
| **Q3** | Vega-Lite | 시계열 선 그래프 | 게임별 평가 수는 어떻게 증가했으며, 축을 바꾸면 무엇이 다르게 보일까? |

여기서 혼동하기 쉬운 용어가 세 가지 있었습니다.

- **평점(Rating)**: 게임에 부여된 점수. 일반적으로 높을수록 좋습니다.
- **평가 수(Number of Ratings)**: 게임을 평가한 횟수 또는 참여 규모를 나타내는 값입니다.
- **순위(Rank)**: 게임의 상대적인 순서. 숫자가 작을수록 상위입니다.

평가 수가 가장 많은 게임이 반드시 평점이나 순위에서도 가장 높은 게임은 아닙니다. 시각화하기 전에 **어떤 숫자를 비교하고 있는지**부터 분명히 해야 했습니다.

## <span style="color:#FEB99C;">2. Q1: Tableau로 비교하기 좋은 표와 막대그래프 만들기</span>

Q1에서는 두 개의 CSV를 사용했습니다.

- `popular_board_game.csv`: 게임 이름, 카테고리, 평점, 평가 수, 플레이 시간, 최소 인원
- `games_detailed_info_filtered.csv`: 카테고리, 메커니즘, 최대 인원

Tableau에서는 필드를 드래그하는 것만으로도 차트의 기본 형태를 만들 수 있습니다. 하지만 **집계 기준을 잘못 정하면 보기에는 그럴듯해도 다른 질문에 답하는 그림**이 만들어집니다.

### ① 솔로 지원 여부로 게임 나누기

첫 번째 작업은 게임을 다음 두 그룹으로 나누는 것이었습니다.

- 최소 인원이 1명인 게임 → **Solo Supported**
- 최소 인원이 1명보다 많은 게임 → **Solo Not Supported**

Tableau 계산 필드는 다음처럼 작성했습니다.

```tableau
IF [min_players] = 1 THEN "Solo Supported"
ELSE "Solo Not Supported"
END
```

그다음 각 그룹 안에서 카테고리별로 다음 네 가지를 보여주었습니다.

1. 게임 수
2. 평가 수가 가장 많은 게임
3. 평균 평점
4. 평균 플레이 시간

제공된 데이터에는 총 **244개**의 게임이 있었고, 이 중 **48개는 솔로 지원**, **196개는 솔로 미지원**이었습니다.

예를 들어 Economic 카테고리는 다음과 같았습니다.

| 솔로 지원 여부 | 게임 수 | 평가 수가 가장 많은 게임 | 평균 평점 | 평균 시간(분) |
|---|---:|---|---:|---:|
| 지원 | 23 | Agricola | 7.95 | 126.52 |
| 미지원 | 65 | Puerto Rico | 7.49 | 105.92 |

이 표에서 중요한 것은 **각 그룹 전체의 평균과, 그 그룹에서 선정한 대표 게임 이름을 동시에 보여준다**는 점입니다.

평가 수가 가장 많은 게임 하나만 남기도록 필터를 걸면 평균도 그 게임만 기준으로 계산될 수 있습니다. 따라서 대표 게임을 찾는 계산과 전체 그룹을 집계하는 계산을 분리해야 했습니다.

### ② 집계 수준을 고정하는 LOD 표현식

그룹별 최대 평가 수를 찾는 데에는 Tableau의 **LOD(Level of Detail)** 표현식을 사용했습니다.

```tableau
{ FIXED [Solo Support], [category] :
    MAX([num_ratings])
}
```

의미는 다음과 같습니다.

> "현재 화면의 배치와 별개로, 솔로 지원 여부와 카테고리 조합별 최대 평가 수를 계산하라."

이 최댓값과 같은 평가 수를 가진 게임의 이름을 가져와 표에 표시했습니다.

여기서 배운 점은 **최댓값 자체를 구하는 것과, 그 최댓값을 가진 행의 이름을 가져오는 것은 별개의 문제**라는 것이었습니다.

또한 평균 플레이 시간에는 구간 문자열인 `playtime`이 아니라 숫자형 필드인 `playtime_num`을 사용했습니다.

```text
playtime     → "(30, 60]" 같은 구간
playtime_num → 45 같은 실제 시간
```

겉보기에는 비슷한 정보를 담고 있어도, 사용할 수 있는 집계 연산은 다릅니다.

### ③ 그룹 막대그래프: 나란히 놓고 비교하기

두 번째 작업은 카테고리마다 플레이 시간 구간별 게임 수를 나란히 배치하는 것이었습니다.

```text
카테고리 → 시간 구간 → 게임 수
```

Tableau의 배치는 다음과 같았습니다.

| 위치 | 필드 |
|---|---|
| Columns | `category`, `playtime` |
| Rows | 게임 수 |
| Color | `playtime` |

시간 구간은 이미 데이터에 제공되어 있었습니다.

```text
≤30분
30분 초과~60분 이하
60분 초과~90분 이하
90분 초과
```

예를 들어 Economic 카테고리는 다음 분포를 보였습니다.

| ≤30분 | (30, 60]분 | (60, 90]분 | >90분 |
|---:|---:|---:|---:|
| 4 | 17 | 23 | 44 |

이 데이터에서는 Economic 게임 중 90분 초과 구간이 가장 많았습니다.

그룹 막대그래프는 모든 막대가 같은 0 기준선에서 시작하므로, **카테고리 안에서 시간 구간별 크기를 비교하기 좋다**는 장점이 있었습니다.

### ④ 누적 막대그래프: 전체 규모와 구성을 함께 보기

세 번째 작업은 카테고리별 게임 수를 하나의 막대로 만들고, 내부를 메커니즘별 색상으로 나누는 것이었습니다.

- 막대 전체 높이 → 해당 카테고리의 게임 수
- 색상 구간 → 메커니즘별 게임 수
- 필터 → `Max.Players`

같은 Dashboard에서 최대 인원을 `2 Players`, `4 Players`로 바꾸어 각각 이미지를 내보냈습니다.

여기서 중요한 조건은 **중복처럼 보이는 행도 삭제하지 않는 것**이었습니다. 이 데이터에서는 각 행을 별개의 게임으로 세도록 요구했기 때문입니다.

예를 들어 Fighting 카테고리의 게임 수는 다음과 같았습니다.

- 최대 인원 2명: **286개**
- 최대 인원 4명: **483개**

누적 막대그래프는 전체 규모와 구성을 함께 보여주지만, 위쪽에 쌓인 구간끼리는 시작점이 달라 세밀한 비교가 어렵습니다.

즉, 그룹 막대와 누적 막대는 단순히 모양이 다른 것이 아니라 **서로 다른 비교에 적합한 표현 방식**이었습니다.

## <span style="color:#FEB99C;">3. Q2: 보드게임 관계를 움직이는 네트워크로 표현하기</span>

Q2에서는 D3.js로 **Force-directed Graph**를 만들었습니다.

보드게임을 원으로, 게임 사이의 연결을 선으로 표현하고, 서로 밀어내거나 끌어당기는 힘을 적용해 배치하는 방식입니다.

제공된 데이터에는 **34개의 노드와 33개의 연결선**이 있었습니다.

### ① 연결 수를 원의 크기와 색으로 표현

각 게임에 연결된 선의 개수인 **degree**를 직접 계산했습니다.

```javascript
link.source.degree += 1;
link.target.degree += 1;
```

여기서 degree는 연결선의 `value` 합계가 아니라 **연결선 자체의 개수**입니다.

계산한 degree를 두 가지 시각적 요소에 연결했습니다.

- 연결이 많을수록 → 원이 커짐
- 연결이 많을수록 → 파란색이 진해짐

```javascript
var radiusScale = d3.scaleSqrt()
  .domain(degreeExtent)
  .range([8, 22]);
```

제곱근 스케일을 사용해 연결 수가 큰 노드를 강조하면서도, 원이 지나치게 커지는 것을 방지했습니다.

제공 데이터에서 `Fourth Dimension`의 degree는 **10**, `Histrio`는 **7**이었습니다. 따라서 연결 수가 1인 게임보다 더 크고 진하게 표현됩니다.

다만 이 네트워크는 과제용으로 수정·단순화된 데이터입니다. 연결이 많다는 이유만으로 실제 시장에서 더 인기 있거나 우수한 게임이라고 해석할 수는 없습니다.

### ② 연결선에도 의미 부여하기

과제에서 지정한 `value`에 따라 선 스타일을 구분했습니다.

| value | 표현 |
|---|---|
| 0 | 회색, 굵은 실선 |
| 1 | 초록색, 가는 점선 |

```javascript
.style("stroke-dasharray", function(d) {
  return d.value === 0 ? "none" : "6,4";
});
```

`"6,4"`는 6픽셀 길이의 선과 4픽셀 간격을 반복한다는 뜻입니다.

색상뿐 아니라 두께와 선 모양도 함께 사용하니, 연결 유형을 구분하기 쉬워졌습니다.

### ③ 원과 이름을 함께 움직이기

게임 이름은 각 원의 오른쪽 위에 굵은 글씨로 표시했습니다.

원과 이름을 하나의 SVG 그룹에 넣으면 함께 이동시킬 수 있습니다.

```html
<g class="node">
  <circle></circle>
  <text>게임 이름</text>
</g>
```

시뮬레이션이 좌표를 갱신할 때 원과 텍스트를 각각 움직이는 대신, 부모 `<g>`에 `translate()`를 적용하는 방식입니다.

이 과정을 통해 SVG의 그룹이 단순한 정리용 요소가 아니라 **여러 시각 요소의 위치와 동작을 함께 관리하는 단위**라는 것을 이해할 수 있었습니다.

### ④ 드래그한 노드를 고정하고, 더블클릭으로 풀기

Force-directed graph는 계속 움직이기 때문에 특정 부분을 자세히 보고 싶을 때 불편할 수 있습니다.

그래서 사용자가 원을 드래그하면 해당 위치에 고정되도록 구현했습니다.

```javascript
d.fx = d3.event.x;
d.fy = d3.event.y;
```

D3 v5에서 `fx`, `fy`는 노드의 고정 좌표입니다. 드래그가 끝나도 이 값을 유지하면 원이 그 자리에 남습니다.

고정된 원은 노란색으로 바꾸고, 더블클릭하면 다음처럼 해제했습니다.

```javascript
d.fx = null;
d.fy = null;
```

색상도 다시 degree에 따른 파란색으로 복구했습니다.

여기서 `d.fixed`는 상태를 기록하는 Boolean 값으로만 사용했습니다. **D3 v5에서 `fixed = true`만 설정한다고 실제로 노드가 고정되는 것은 아니었습니다.**

## <span style="color:#FEB99C;">4. Q3: Vega-Lite로 시간의 흐름과 축의 효과 비교하기</span>

Q3에서는 2016년 11월부터 2020년 8월까지, 8개 보드게임의 평가 수 변화를 선 그래프로 표현했습니다.

D3가 요소를 만들고 좌표를 지정하는 절차를 직접 작성하는 방식이라면, Vega-Lite는 **"어떤 필드를 어떤 시각 요소에 연결할지"를 선언하는 방식**에 가깝습니다.

```javascript
encoding: {
  x: {
    field: "date",
    type: "temporal"
  },
  y: {
    field: "countNum",
    type: "quantitative"
  },
  color: {
    field: "gameName",
    type: "nominal"
  }
}
```

### ① 넓은 데이터를 긴 데이터로 바꾸기

CSV에는 게임별 값이 서로 다른 열에 들어 있었습니다.

```text
date, Catan=count, Catan=rank, Dominion=count, Dominion=rank, ...
```

선 그래프에서는 다음과 같은 형태가 더 다루기 편합니다.

```text
date         gameName   countNum
2016-11-01   Catan      62588
2016-11-01   Dominion   51915
```

Vega-Lite의 `fold` 변환으로 여러 평가 수 열을 세로로 펼치고, 열 이름에서 게임 이름을 추출했습니다.

이 과정은 **시각화에 적합한 데이터 구조를 만드는 것 자체가 중요한 전처리 작업**이라는 점을 보여주었습니다.

### ② 선의 높이와 원 안의 숫자는 다른 정보

기본 차트에서는 평가 수를 선의 높이로 표현하고, 추가 차트에서는 네 게임의 순위를 원 안에 넣었습니다.

예를 들어 2017년 1월 Catan은 다음과 같았습니다.

- 평가 수: **64,164**
- 순위: **219**

따라서 원의 위치는 Y=64,164이고, 원 안에는 `219`가 표시됩니다.

**평가 수의 증가와 순위의 변화는 서로 다른 정보**이므로, 같은 그림 안에서도 표현 수단을 구분해야 했습니다.

### ③ 같은 데이터를 선형·제곱근·로그 축으로 보기

최종적으로 네 개의 차트를 만들었습니다.

| 차트 | Y축 | 순위 표시 |
|---|---|---|
| A | 선형 | 없음 |
| B | 선형 | 있음 |
| C1 | 제곱근 | 있음 |
| C2 | 로그 | 있음 |

축에 따라 화면에서 사용하는 간격은 달라집니다.

$$
f(y)=y,\qquad f(y)=\sqrt{y},\qquad f(y)=\log(y)
$$

- **선형 축**: 절대적인 수량 차이를 비교하기 좋습니다.
- **제곱근 축**: 큰 값의 차이를 압축하면서 작은 값의 변화를 더 드러냅니다.
- **로그 축**: 같은 배율의 증가를 같은 간격으로 보여줍니다.

여기서 원본 값을 직접 제곱근이나 로그로 바꿔 저장한 것은 아닙니다. **원본 데이터는 유지하고, 위치를 계산하는 스케일만 변경**했습니다.

로그 축은 0을 표현할 수 없다는 점도 고려해야 했습니다. 제공 데이터에는 평가 수 0이 없었지만, 축의 시작은 양수로 설정했습니다.

### ④ 디버깅 경험: 보기에는 맞아도 명세는 다를 수 있다

자동 채점에서는 X축의 스케일이 `utc`가 아니라 `time`이어야 한다는 오류가 발생했습니다.

둘 다 시간 데이터를 표현하지만, 내부 스케일 종류는 다릅니다.

```javascript
scale: {
  type: "time"
}
```

으로 바꾸면서 날짜 생성과 CSV 파싱도 같은 로컬 시간 기준으로 맞췄습니다.

또 하나는 3개월 간격의 순위 원 표시였습니다.

처음에는 미리 만든 날짜 배열에 포함되는지 검사했지만, 채점기는 명시적인 월 기반 샘플링 패턴을 요구했습니다.

```javascript
filter: "month(datum.date) % 3 == 0"
```

월 번호가 0부터 시작하므로, 이 조건은 1월·4월·7월·10월을 선택합니다. X축 눈금도 같은 달에 배치해 원과 눈금을 맞췄습니다.

이 경험을 통해 **시각적으로 동일한 결과와 구현 명세를 충족하는 결과가 항상 같은 것은 아니다**라는 점을 배웠습니다.

## <span style="color:#FEB99C;">5. 전반부 요약: 도구마다 잘하는 일이 다르다</span>

세 도구를 사용하며 느낀 차이는 다음과 같습니다.

| 도구 | 장점 | 특히 신경 써야 할 부분 |
|---|---|---|
| **Tableau** | 빠르게 집계하고 차트를 구성할 수 있음 | 집계 수준, 필터, 필드 타입 |
| **D3.js** | 요소와 상호작용을 세밀하게 제어할 수 있음 | 좌표, DOM 구조, 이벤트, 상태 관리 |
| **Vega-Lite** | 데이터와 시각 요소의 관계를 간결하게 선언 | 데이터 변환, 인코딩, 레이어, 스케일 |

이번 전반부를 관통하는 핵심은 다음과 같았습니다.

> **"좋은 시각화는 차트 종류를 고르는 것에서 끝나지 않는다. 집계 기준, 색상, 크기, 축, 상호작용이 모두 같은 질문을 향해야 한다."**
